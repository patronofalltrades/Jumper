## Ledger notes

Claude notes (not Hanif's words).

- How it works. `components/build/level-path.tsx` (new, client) draws the level list that was in `app/p/[project]/page.tsx`. Before the first paint, it reads the state that the map showed last time (`lib/game/map-progress.ts`, from `localStorage`, per user and project), decides with `animateFrom`, and saves the state that the map shows now. A pass or more XP since then starts the animation from the stored state. The end state comes two frames later, so the CSS transitions run: the check mark, the path segment below the passed level, the next level's ring, and the Volt marker. The XP counts up with `requestAnimationFrame` over 1.2 s, with `countValue`.
- Server side. `app/p/[project]/page.tsx` reads `profiles.xp` with the passed levels, and passes them to `LevelPath`. No migration, no new package.
- Choices made. (1) The key is `jumper:<user>:map/<project>`. It has the saved-board prefix of the user, so the account deletion (`clearUserSaves`) clears it too. (2) The map shows the XP total (`profiles.xp`, the same number as the lobby) as a chip above the path. The map had no XP number before, and the issue asks for one. (3) The state is saved when the map opens, not when the animation ends. A learner who leaves during the animation does not see it again. (4) A first visit, a visit with no change, and a stored state that is newer than the server show the end state with no animation. (5) Reduced motion shows the end state with no animation. (6) The Volt marker does not slide between levels. It hops in on the new level (the `rise-in` keyframe in `app/globals.css`).
- Bugs found by the browser check and fixed before the commit (the first version of the component). (a) The server HTML painted the end state (80 XP, level 2 done) for a moment before hydration, then the page jumped back to the stored state (40 XP). Fix: the path stays `invisible` until the layout effect has read the stored state. (b) The transition classes were on the element from the start, so the check mark and the path fill began at their server values and reversed 2 frames later. The check mark and the fill never showed their start state. Fix: the transition classes are added only with the end state (`moving`). Both were found by recording every animation frame from page start (a temporary init script, not committed).
- Lint. `react-hooks/set-state-in-effect` flagged the stored-state decision. The repo has the same disable for the same case (`components/build/build-view.tsx`, saved progress in the browser), so the component uses it with a reason.
- Tests. Red first: `tests/map-progress.test.ts` (8 tests) before `lib/game/map-progress.ts`. The red run failed at the import (the module did not exist). Green after the module. A mutation check (the stored state replaced by the server state) makes 2 tests fail, then the file was reverted.
- Browser check. A temporary route under `app/s/mapdemo` (public prefix, so no log-in; removed before the commit) with placeholder Supabase values and sample levels, in Chromium with Playwright. Results: (1) stored 1 level and 40 XP, server 2 levels and 80 XP: start state paints at 40 XP with level 2 open; the check mark and the path fill grow over about 500 ms; the marker moves to level 3; XP reaches 80 at about 1.3 s. (2) A second load with the same server state: 80 XP, no animation. (3) First visit with nothing stored: no animation. (4) Reduced motion with a stored state: 80 XP at once. No page errors. The only console errors came from the temporary route itself (its `searchParams` read outside `Suspense`, which Next.js reports for prerendering); the component has none. Screenshots at 1280 x 800 (mid-animation and end) and 390 x 844 (end) are in `prompts/pass-progress-screens/`.
